# KARDS 卡组存档小程序 · 技术方案

> 状态：待评审
> 定位：微信内「卡组码一键存档 + 秒查」的极简工具
> 原则：本地优先、零门槛、不碰组卡器、不碰大而全平台

---

## 0. 背景与定位

**痛点**：KARDS 游戏内卡组槽位有限（约 30 个），玩久了必须删旧卡组才能存新的；用备忘录存卡组信息又不方便查找。

**竞品结论**（已调研）：
- 网页端「卡组存档」已被 [KARDS DECKER](https://1939.giaory.xyz/) 覆盖（有账号 + 我的卡组 + 卡组广场）。
- 微信小程序形态「卡组存档 + 秒查」是**空位**，无人占据。
- 组卡器赛道已卷（fk1939 / KD / KDB / 军械库 / KardsCN / 营地），不做。

**差异化**：微信内秒开、免记网址、免下载；只做「存 + 查」，比 KD 更轻、更顺手。

---

## 1. MVP 范围

### P0（首版必须）
1. 粘贴 KARDS 卡组代码 → 本地解析成结构化卡组（40 张卡牌 + 中文名 + 费用曲线 + 阵营）
2. 卡组列表：保存 / 命名 / 删除 / 搜索 / 按阵营筛选 / 自定标签
3. 卡组详情：40 张卡牌、费用曲线、阵营；一键复制卡组代码回游戏
4. 本地持久化 + 导出 / 导入备份（JSON）
5. 卡牌数据本地缓存（KD 全量 1613 张，启动时拉取）

### P1（后续迭代）
- 微信 openid 静默登录 + 云同步（可选，跨设备）
- 卡组图片生成（分享用）
- 手动组卡（从卡牌库选卡）

## 2. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 小程序框架 | 原生微信小程序（TS） | 功能简单、无多端需求、最轻、审核直接 |
| 后端 | MVP 无后端 | 纯前端 + 本地 storage；数据来自 KD 公开接口 |
| 卡牌数据源 | KD 公开接口 `GET /api/v1/cards` | 免费、无需 key、含中文名与官方卡图 |
| 卡图 | KD `image_proxy_url` 代理 | 已处理官方卡图防盗链 |
| 卡组存档 | 本地 storage（`wx.setStorageSync`） | 数据量小，零门槛；P1 再加云同步 |

> 备选框架：若后续想出 H5 / App，可迁移 uni-app（Vue3）。首版不建议，避免过度设计。

## 3. 数据设计

### 3.1 卡牌索引（从 KD 拉全量后精简缓存）

以 `import_id`（2 字符短码）为 key：

```jsonc
{
  "rn": {
    "card_id": "hell_on_wheels",
    "name_zh": "地狱之轮",
    "name_en": "HELL ON WHEELS",
    "faction": "USA",
    "type": "order",
    "rarity": "Elite",
    "kredits": 4,
    "attack": 0,
    "defense": 0,
    "set": "BloodAndIron",
    "image_proxy_url": "https://1939.giaory.xyz/img-proxy?url=..."
  }
}
```

- 全量 1613 张，精简后约 200–300KB，分片存 storage（单 key 有 1MB 上限）。
- 卡图不缓存，`<image>` 按需远程加载。

### 3.2 卡组对象

```jsonc
{
  "id": "uuid",
  "name": "自命名",
  "deck_code": "%%4|...",        // 原始代码，复制回游戏用它（不重新生成）
  "main_faction": "Soviet",
  "ally_faction": null,
  "cards": [ { "import_id": "rn", "count": 2 } ],
  "tags": ["快攻"],
  "created_at": 1234567890,
  "updated_at": 1234567890
}
```

## 4. 卡组代码格式（核心算法，已逆向 KD 确认）

### 4.1 格式

```
%%[主阵营码][盟国码]|[段0];[段1];[段2];[段3]
```

- **阵营码**：`1`=德国 `2`=英国 `3`=日本 `4`=苏联 `5`=美国 `6`=法国 `7`=意大利 `8`=波兰 `9`=芬兰 `10`/`a`=澳新军团
- **盟国码**：可选（单阵营卡组省略）
- **段**：用 `;` 分隔；第 n 段（0 起）的卡牌数量 = n+1（段0=1张、段1=2张、段2=3张、段3=4张）
- **段内**：`import_id` 每 2 个字符一张卡（区分大小写，如 `rn`、`3L`、`6A`）

> 逆向依据：KD 构筑器源码中的正则 `/^%%(10|[1-9a-fA-F])(10|[1-9a-fA-F])?\|(.+)$/i` 与分段逻辑 `b.slice(v, v+2)`、`w = y+1`。

### 4.2 解析伪代码

```
m = code.match(/^%%(10|[1-9a-fA-F])(10|[1-9a-fA-F])?\|(.+)$/)
mainFaction = factionMap[m[1]]
allyFaction = m[2] ? factionMap[m[2]] : null
segments = m[3].split(';')
for (y, seg) in segments:
    count = y + 1
    for i in 0..seg.length step 2:
        importId = seg[i : i+2]
        card = cardIndex[importId]
        cards.push(card, ×count)
```

### 4.3 生成（反向，仅备份/导出用）

按卡牌数量分 4 个桶（1/2/3/4 张）→ 每桶 `import_id` 拼接 → `;` 连接 → 前缀 `%%[主阵营码][盟国码]|`。

> ⚠️ 复制回游戏一律用原始 `deck_code`，不做重新生成，避免格式漂移。

## 5. 数据流

1. **启动 / 数据版本过期**：调 KD `GET /api/v1/cards?limit=50&page=1..33` 拉全量 → 转精简索引 → 分片存 storage。
2. **添加卡组**：粘贴代码 → 本地解析 → 生成卡组对象 → 存 storage。
3. **列表**：读 storage → 渲染 + 搜索 / 阵营 / 标签筛选。
4. **详情**：按卡牌索引渲染 40 张卡 + 费用曲线；卡图远程加载。
5. **复制代码**：取卡组的 `deck_code` 原样写入剪贴板。

## 8. 合规

- **卡牌数据**：来自 KARDS DECKER 公开接口（KD 主动公开 `/api-docs`，默许第三方读取）。
- **卡图**：官方资产，版权归 1939 Games；遵守其 Community Content Policy（非商业、标注版权）。
- **关于页**：声明「非官方工具」「数据来源 KD」「卡图版权 1939 Games」。

---

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| KD 接口不稳定 / 停服 | 本地缓存 + 数据版本号；缓存过期仍可用旧数据兜底 |
| 极少数卡 `name_zh` 为空 | 展示回退 `name_en` |
| storage 大小限制 | 卡牌索引分片；卡图不缓存 |
| 卡组代码格式未来变化 | 解析容错；复制回游戏用原始代码 |
| 微信审核（涉第三方游戏数据） | 非官方声明、非商业、数据来源标注 |
| `import_id` 潜在重复 | 拉数据时校验唯一性，重复则告警 |

---

## 10. 里程碑

- **M1 数据层**：拉 KD 全量 + 缓存；卡组代码解析/生成（含单元自测，用真实卡组代码样本验证）
- **M2 核心闭环**：列表 + 添加（粘贴代码）+ 详情 + 复制代码
- **M3 检索与备份**：搜索 / 阵营 / 标签筛选 + 导出导入 JSON
- **M4 收尾**：合规声明 + 打磨 + 提交微信审核
